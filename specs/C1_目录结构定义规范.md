# C1 目录结构定义规范

## 1. 总则

### 1.1 目标
定义管线生成产物（后端Flask项目、前端Vue3项目、部署配置）的目录结构标准，确保代码生成、检查、修复各环节对目录布局有一致理解，为 C2（代码块输出格式）、C5（导入规范）提供路径基础，为 A1（Agent上下文清单的 `project_structure` 字段）提供结构化数据。

### 1.2 定位

| 维度 | 说明 |
|------|------|
| **与A1的关系** | A1定义Backend/Frontend Agent的生成顺序和上下文清单中的`project_structure`字段；C1定义该字段的具体Schema和目录布局 |
| **与D3的关系** | D3 §5.1定义管线运行时目录（`output/{pipeline_id}/`）；C1定义`artifacts/backend/`和`artifacts/frontend/`内部的**项目源码目录** |
| **与C2的关系** | C2定义代码块输出格式中的文件路径声明；C1定义这些路径对应的目录树，确保路径与结构一致 |
| **与C5的关系** | C5定义导入路径规范；C1定义目录层级，导入路径必须基于C1定义的目录结构 |
| **与P4的关系** | P4定义跨文件衔接时的导入声明约束；衔接路径的正确性依赖于C1目录定义 |

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| **架构分层映射** | 目录层级直接映射ABC三层架构（接口层→抽象实现层→设备扩展层），目录即架构 |
| **模块边界清晰** | 每个业务模块对应一个独立子目录，模块间通过接口层解耦 |
| **生成顺序友好** | 目录组织与A1定义的生成顺序对齐，基础设施在前、业务模块在中、注册入口在后 |
| **前后端对称** | 前后端业务模块一一对应（login/user/alert/log/monitor/network），便于契约校验 |
| **可校验可枚举** | project_structure JSON可由代码完全枚举，支持Validate Agent的目录完整性检查 |

### 2.2 目录层级与ABC架构映射

| 目录层级 | 架构角色 | 说明 |
|---------|---------|------|
| `app/api/*_interface.py` | **A — 接口层** | ABC抽象基类，定义业务方法签名 |
| `app/services/*.py` | **B — 抽象实现层** | 继承ABC接口，实现通用业务逻辑 |
| `app/device/*.py` | **C — 设备扩展层** | 继承Service层，按设备类型覆盖特定行为 |
| `app/api/*.py`（非interface） | **路由层** | Blueprint路由，调用Service层方法，不包含业务逻辑 |
| `app/models/*.py` | **数据层** | SQLAlchemy模型，仅定义数据结构，不含业务方法 |

### 2.3 目录与生成顺序映射

A1 §2.6定义的Backend生成顺序与目录的对应关系：

| 生成顺序 | 目录/文件 | 层级 |
|---------|----------|------|
| 1. 基础设施层 | `app/__init__.py`, `app/config.py`, `app/extensions.py`, `app/utils/*.py`, `app/models/base.py` | 基础 |
| 2. 用户管理 | `app/models/user.py` → `app/api/user_interface.py` → `app/services/user.py` → `app/api/user.py` | 业务模块 |
| 3. 告警管理 | `app/models/alert.py` → `app/api/alert_interface.py` → `app/services/alert.py` → `app/api/alert.py` | 业务模块 |
| 4. 日志管理 | `app/models/log.py` → `app/api/log_interface.py` → `app/services/log.py` → `app/api/log.py` | 业务模块 |
| 5. 系统监控 | `app/models/monitor.py` → `app/api/monitor_interface.py` → `app/services/monitor.py` → `app/api/monitor.py` + `app/websocket/monitor.py` | 业务模块 |
| 6. 网络状态监控 | `app/models/network_status映射.py` → `app/api/network_interface.py` → `app/services/network.py` → `app/api/network.py` + `app/websocket/alert.py` | 业务模块 |
| 7. 路由注册 | `app/api/__init__.py`（Blueprint注册）, `run.py` | 入口 |

**模块内生成顺序**：`Model → Interface(ABC) → Service(实现) → Router(Blueprint)`

### 2.4 目录与设备扩展

`app/device/` 目录采用Strategy模式，与Service层配合：

```
Service层（通用逻辑）  ←── 调用 ──→  Device层（设备特定逻辑）
    │                                        │
    ├── UserManager                          ├── FirewallStrategy
    │   └── get_device() → device.xxx()     ├── IDSStrategy
    │                                        └── VPNStrategy
    └── ...
```

- `app/device/__init__.py` 提供 `get_device_type()` 函数，从Flask Config读取设备类型
- 各Strategy实现DeviceStrategy ABC，覆盖需差异化的方法
- Service层通过 `get_device_type()` 获取当前设备策略实例，委托设备相关操作

## 6. 目录校验规则

### 6.1 生成时校验

Backend/Frontend Agent在生成每个文件时，必须校验：

| 校验项 | 规则 | 失败处理 |
|--------|------|---------|
| 路径合法性 | 文件路径必须符合C1定义的目录树 | 拒绝生成，修正路径 |
| 目录存在性 | 写入文件前确保父目录已创建 | 自动创建目录 |
| 模块归属 | 文件必须归属于正确的业务模块 | 拒绝生成，确认模块 |
| 扩展名一致性 | Python文件`.py`，Vue文件`.vue`，JS文件`.js` | 拒绝生成，修正扩展名 |

### 6.2 Validate Agent校验

Validate Agent在检查阶段，对目录结构的校验：

| 校验项 | 规则 | 检查层级 |
|--------|------|---------|
| 必需文件存在 | infrastructure和modules中定义的所有文件必须存在 | L1静态分析 |
| 孤儿文件检测 | 不在project_structure中的文件为孤儿文件，需确认 | L1静态分析 |
| 目录层级正确 | `api/`下不能有Service逻辑，`services/`下不能有路由定义 | L2 LLM审查 |
| ABC分层正确 | Interface文件只含ABC定义，Service文件必须继承对应Interface | L2 LLM审查 |
| 前后端模块对应 | 前端`api/*.js`的模块名与后端`api/*.py`的模块名一一对应 | L2.5契约校验 |

### 6.3 孤儿文件处理

发现不在project_structure中的文件时：

1. 标记为 `orphan_file`
2. 判断是否为合法的新增文件（如设备扩展策略）
3. 合法 → 追加到project_structure对应位置
4. 不合法 → 标记为待清理，上报Orchestrator

## 7. 目录扩展规则

### 7.1 设备扩展

当需要新增设备类型（如VPN网关）时：

1. 在 `app/device/` 下新增 `{device}.py`，实现 `DeviceStrategy` ABC
2. 在 `app/device/__init__.py` 注册新策略
3. 在 `project_structure.backend.device_strategies` 追加路径
4. Service层无需修改（通过策略模式自动路由）

### 7.2 业务模块扩展

当需要新增业务模块时：

1. 按模块内生成顺序创建：`Model → Interface → Service → Router`
2. 前端同步创建：`api → store → view`
3. 在 `project_structure` 的 `modules` 对象中追加模块条目
4. 更新 `app/api/__init__.py` 注册新Blueprint
5. 更新前端 `router/index.js` 添加新路由

### 7.3 公共组件扩展

前端新增公共组件时：

1. 按类别放入对应子目录：`common/`、`business/`、`charts/`
2. 在 `project_structure.frontend.shared_components` 追加路径
3. 组件命名PascalCase（C3命名规范）

## 8. 与管线运行时目录的关系

C1定义的目录结构位于D3 §5.1管线运行时目录的 `artifacts/` 下：

```
output/{pipeline_id}/
├── artifacts/                    ← D3定义
│   ├── backend/                  ← C1 §2 后端项目目录
│   │   └── app/...
│   ├── frontend/                 ← C1 §3 前端项目目录
│   │   └── src/...
│   └── devops/                   ← C1 §4 DevOps产物目录
│       └── docker/...
├── versions/                     ← D2版本链
├── state/                        ← 管线状态
├── logs/                         ← 运行日志
├── errors/                       ← 错误数据
└── tmp/                          ← 临时文件
```

- C1的`project_structure`中路径均相对于 `artifacts/` 目录
- Backend Agent写入 `artifacts/backend/`
- Frontend Agent写入 `artifacts/frontend/`
- DevOps Agent写入 `artifacts/devops/`

## 9. 与其他规范的联动

### 9.1 与C2的联动

| C1定义 | C2消费方式 |
|--------|----------|
| 目录树 | C2代码块输出格式中的文件路径必须与C1目录对齐 |
| 模块归属 | C2按模块定义输出格式差异（如WebSocket模块额外输出事件处理器） |

### 9.2 与C5的联动

| C1定义 | C5消费方式 |
|--------|----------|
| 目录层级 | C5导入路径必须基于C1定义的目录层级 |
| 模块划分 | C5本地导入分组按C1模块划分 |
| ABC分层 | C5定义跨层导入规则（Router→Service→Model的导入方向约束） |

### 9.3 与P4的联动

| C1定义 | P4消费方式 |
|--------|----------|
| 生成顺序 | P4衔接约束按C1生成顺序确定依赖关系 |
| 模块内顺序 | P4模块内衔接（Model→Interface→Service→Router）依赖C1定义 |
| project_structure | P4从A4上下文中读取project_structure确定已生成文件 |
