# D4 错误数据规范

## 1. 总则

### 1.1 目标
定义管线中错误数据的完整生命周期——从产生、分类、富化、传播、聚合、持久化到归档，确保错误数据结构化、可追溯、可关联、可查询，为容错决策（A5）、版本回退（D2）、持久化恢复（D3）和代码检查（V系列）提供统一的数据基础。

### 1.2 定位

| 维度 | 说明 |
|------|------|
| **与A3的关系** | A3定义了7种消息类型和18个错误码（6.1节）；D4扩展错误分类体系、定义错误数据模型、补充错误传播路径中的数据结构 |
| **与A5的关系** | A5定义了容错机制（L1-L4）、降级策略、断路器、补偿事务；D4定义这些机制消费和产出的错误数据格式，是容错决策的输入 |
| **与D1的关系** | D1定义了error_context.json的Schema（10章）；D4扩展该Schema，新增错误聚合、关联、生命周期字段 |
| **与D2的关系** | D2定义了版本链管理；D4定义错误数据的版本化策略和错误快照的版本管理 |
| **与D3的关系** | D3定义了持久化和原子写入；D4定义错误数据的持久化层级、日志格式和故障恢复中的错误数据重建 |

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| **结构化优先** | 每个错误都有唯一标识、分类、层级、时间戳，而非自由文本 |
| **渐进富化** | 错误数据在传播过程中逐层补充上下文，不要求初始报告包含全部信息 |
| **去重聚合** | 同一根源的多次错误聚合为错误簇，避免日志爆炸 |
| **爆炸半径标注** | 每个错误明确标注影响范围，支持A5的隔离决策 |
| **可追溯可关联** | 错误之间可建立因果链，支持根因分析 |

## 2. 错误分类体系

### 2.1 多维分类

A3定义了18个错误码，按处理策略分为L1-L4四级。D4在此基础上，增加三个分类维度，形成多维分类矩阵：

| 维度 | 定义者 | 说明 |
|------|--------|------|
| **错误码（error_code）** | A3 | 18个具体错误码，标识错误类型 |
| **异常级别（error_level）** | A2/A5 | L1/L2/L3/L4，标识容错策略 |
| **来源层级（source_layer）** | D4 | 错误发生在管线的哪个层级 |
| **业务域（business_domain）** | D4 | 错误影响哪个业务模块 |

### 2.2 来源层级分类

| 来源层级 | 代号 | 说明 | 示例 |
|---------|------|------|------|
| **基础设施** | `INFRA` | LLM/RAG/文件系统等外部依赖 | LLM超时、RAG检索失败、磁盘空间不足 |
| **数据层** | `DATA` | JSON产物的Schema/版本/内容问题 | Schema校验失败、版本不匹配、字段缺失 |
| **逻辑层** | `LOGIC` | Agent生成逻辑或业务规则错误 | 代码语法错误、路由缺失、接口参数不一致 |
| **编排层** | `ORCHESTRATION` | 调度/通信/状态流转错误 | Agent超时、回退深度超限、消息格式错误 |

### 2.3 业务域分类

| 业务域 | 代号 | 说明 |
|--------|------|------|
| **核心业务** | `CORE` | 用户管理、告警管理模块 |
| **一般业务** | `GENERAL` | 日志管理、系统监控、网络状态监控模块 |
| **公共基础** | `COMMON` | 数据库、认证、框架基础设施 |
| **非业务** | `NON_BUSINESS` | LLM调用、文件IO、管线调度等纯技术层 |

除A3定义的18个错误码外，D4补充以下在D1/D2/D3中提及但未纳入A3的错误码：

| 错误码 | 异常级别 | 来源层级 | 说明 | 产出者 |
|--------|---------|---------|------|--------|

| `INPUT_BUSINESS_INVALID` | L2 | LOGIC | 输入产物业务逻辑不合理 | 消费Agent |

> 以上错误码的异常级别和来源层级遵循D3第2.2节和D2第5.3节中已定义的处理逻辑，D4仅补充其正式编码和分类归属。

## 4. 渐进富化

### 4.1 富化阶段

错误数据在生命周期中逐层补充上下文信息，不要求初始报告包含全部字段：

```
错误发生（Agent内部）
  │
  ├─ 第1层：核心字段（必须立即填写）
  │    error_id, timestamp, pipeline_id, agent, stage,
  │    error_level, error_code, message, lifecycle.state=detected
  │
  ├─ 第2层：分类字段（Agent可立即判定）
  │    source_layer, business_domain, blast_radius,
  │    affected_files, affected_modules, retry_count, fix_rounds
  │
  ├─ 第3层：传播字段（上报Orchestrator时补充）
  │    lifecycle.state=propagated, attempted_actions,
  │    context_snapshot_path, suggestion,
  │    root_error_id, input_artifacts
  │
  ├─ 第4层：关联字段（Orchestrator聚合时补充）
  │    cluster_id, related_error_ids, enrichments,
  │    lifecycle.state=handling
  │
  └─ 第5层：关闭字段（容错完成后补充）
       lifecycle.state=resolved/escalated,
       lifecycle.resolved_at, lifecycle.resolution
```

### 4.2 富化规则

| 富化者 | 可添加的字段 | 触发时机 |
|--------|------------|---------|
| **产出Agent** | 核心字段+分类字段 | 错误发生时 |
| **产出Agent** | 第3层字段 | 上报Orchestrator时 |
| **Orchestrator** | cluster_id、related_error_ids | 接收error消息后聚合 |
| **Orchestrator** | enrichments记录 | 每次富化操作后 |
| **容错执行者** | attempted_actions、retry_count、fix_rounds | 每次容错动作后 |
| **Orchestrator** | lifecycle关闭字段 | 容错完成/升级后 |

### 4.3 富化示例

```
1. Backend Agent检测到STATIC_ANALYSIS_FAILED
   → 产出ErrorRecord:
     {
       "error_id": "err-001",
       "error_level": "L2",
       "error_code": "STATIC_ANALYSIS_FAILED",
       "source_layer": "LOGIC",
       "business_domain": "CORE",
       "blast_radius": "file",
       "affected_files": ["app/services/user.py"],
       "lifecycle": {"state": "detected", "detected_at": "..."}
     }

2. Backend Agent完成文件级修复
   → 富化ErrorRecord:
     {
       "attempted_actions": [
         {"action": "L2_fix", "result": "success", "detail": "修复3个语法错误"}
       ],
       "lifecycle": {"state": "resolved", "resolved_at": "...", "resolution": "fix_applied"}
     }

3. 若修复失败，上报Orchestrator
   → 富化ErrorRecord:
     {
       "attempted_actions": [
         {"action": "L2_fix", "result": "failed", "count": 3}
       ],
       "suggestion": "rollback_to_api_agent",
       "context_snapshot_path": "state/agent_contexts/backend_context_dv5.json",
       "lifecycle": {"state": "propagated", "propagated_at": "..."}
     }
```

## 5. 错误生命周期

### 5.1 生命周期状态

```
                 ┌─────────────────────────────────────┐
                 │                                     │
                 ▼                                     │
[detected] ──→ [propagated] ──→ [handling] ──→ [resolved]
                                    │
                                    ├────────────→ [escalated]
                                    │                  │
                                    │                  ▼
                                    │          [archived]
                                    │
                                    └────────────→ [archived]
```

| 状态 | 含义 | 触发条件 | 下一个合法状态 |
|------|------|---------|--------------|
| **detected** | 错误刚被检测到 | Agent内部检测 | propagated、handling、resolved |
| **propagated** | 错误已上报Orchestrator | Agent发送error消息 | handling |
| **handling** | Orchestrator正在处理 | Orchestrator接收error消息后 | resolved、escalated |
| **resolved** | 错误已解决 | 容错成功 | archived |
| **escalated** | 错误已升级 | 容失败/超出能力范围 | archived |
| **archived** | 错误已归档 | 管线完成或终止 | —（终态） |

### 5.2 各级别的典型生命周期

| 异常级别 | 典型路径 | 说明 |
|---------|---------|------|
| **L1** | detected → handling → resolved | Agent内部重试成功，不传播到Orchestrator |
| **L1(重试失败)** | detected → propagated → handling → resolved/escalated | 重试耗尽后上报 |
| **L2** | detected → handling → resolved | Agent内部修复成功 |
| **L2(修复失败)** | detected → propagated → handling → resolved/escalated | 修复耗尽后上报 |
| **L3** | detected → propagated → handling → resolved | Orchestrator协调回退成功 |
| **L3(回退失败)** | detected → propagated → handling → escalated | 回退级联超限 |
| **L4** | detected → propagated → handling → escalated | 直接触发人工介入 |

### 5.3 生命周期状态转换规则

```
detected:
  → resolved: L1重试成功 / L2修复成功（Agent内部消化）
  → propagated: L1/L2容失败，上报Orchestrator
  → handling: L3/L4由Orchestrator直接处理

propagated:
  → handling: Orchestrator接收error消息并开始决策

handling:
  → resolved: 容错动作成功（重试/修复/回退/降级）
  → escalated: 容失败/超出Orchestrator能力范围（升级到L4人工介入）

resolved:
  → archived: 管线完成或归档时

escalated:
  → archived: 管线完成或终止时
```

### 5.4 L1错误的生命周期特殊规则

L1错误在Agent内部消化时，生命周期简化：

```
L1 detected → L1 handling → L1 resolved
  （不产生propagated状态，不上报Orchestrator）

L1 detected → L1 handling(failed) → L1 propagated
  （重试耗尽后升级为propagated，纳入Agent级L1重试计数）
```

**L1错误的记录策略**：

| 场景 | 是否记录到errors/目录 | 是否记录到agent日志 |
|------|---------------------|-------------------|
| L1重试1次即成功 | 不记录（噪音过多） | 记录（INFO级别） |
| L1重试多次后成功 | 不记录 | 记录（WARNING级别） |
| L1重试耗尽 | 记录 | 记录（ERROR级别） |

## 6. 错误聚合与去重

### 6.1 聚合场景

同一根源可能触发多次同类错误，例如：
- Backend逐文件生成时，多个文件因同一Schema问题产生STATIC_ANALYSIS_FAILED
- LLM API限流期间，连续多次LLM_RATE_LIMIT
- api_def.json变更后，Backend多个模块的CONTRACT_MISMATCH

### 6.2 聚合规则

**聚合键（clustering_key）**：

| 错误码 | 聚合键 | 聚合窗口 | 说明 |
|--------|--------|---------|------|
| `LLM_TIMEOUT` | agent + error_code | 5 min | 同一Agent连续超时归为同一簇 |
| `LLM_RATE_LIMIT` | agent + error_code | 5 min | 限流期间归为同一簇 |
| `STATIC_ANALYSIS_FAILED` | agent + error_code + module | 单次dispatch | 同模块的静态分析错误归为同一簇 |
| `CONTRACT_MISMATCH` | agent + error_code | 单次dispatch | 同次dispatch的契约错误归为同一簇 |
| `RUNTIME_IMPORT_ERROR` | agent + error_code + module | 单次dispatch | 同模块的导入错误归为同一簇 |
| 其他 | agent + error_code | 10 min | 默认聚合规则 |

### 6.3 错误簇结构

```json
{
  "cluster_id": "uuid",
  "pipeline_id": "uuid",
  "clustering_key": {
    "agent": "backend_agent",
    "error_code": "STATIC_ANALYSIS_FAILED",
    "module": "user_management",
    "window_start": "2026-04-30T00:15:00+08:00",
    "window_end": "2026-04-30T00:15:30+08:00"
  },
  "first_error_id": "err-001",
  "last_error_id": "err-005",
  "error_count": 5,
  "error_ids": ["err-001", "err-002", "err-003", "err-004", "err-005"],
  "aggregate_blast_radius": "module",
  "aggregate_error_level": "L2",
  "common_affected_files": [
    "app/services/user.py",
    "app/views/user_view.py",
    "app/models/user.py"
  ],
  "root_cause_hypothesis": "user_management模块缺少role_id字段定义",
  "created_at": "2026-04-30T00:15:00+08:00",
  "updated_at": "2026-04-30T00:15:30+08:00"
}
```

### 6.4 聚合后的爆炸半径升级

当同一簇内错误数量达到阈值时，爆炸半径自动升级：

| 条件 | 爆炸半径升级 | 说明 |
|------|------------|------|
| 同簇错误 ≥ 3 且 blast_radius=file | file → module | 多文件错误影响整个模块 |
| 同簇错误 ≥ 3 且 blast_radius=module | module → agent | 多模块错误影响整个Agent |
| 同簇错误涉及 ≥ 2 个并行Agent | agent → pipeline | 并行Agent都出错影响整条管线 |

### 6.5 聚合后的异常级别升级

| 条件 | 异常级别升级 | 说明 |
|------|------------|------|
| 同簇错误在L1重试后仍持续 | L1 → L2 | 重试无效说明非暂时性问题 |
| 同簇错误在L2修复后仍持续 | L2 → L3 | 修复无效需要回退 |
| 同簇错误在L3回退后仍持续 | L3 → L4 | 回退无效需要人工介入 |

## 7. 错误因果链

### 7.1 因果关系类型

多个错误之间可能存在因果关系：

| 因果类型 | 代号 | 说明 | 示例 |
|---------|------|------|------|
| **直接因果** | `DIRECT` | A错误直接导致B错误 | api_def.json缺失字段 → Backend代码生成失败 |
| **传播因果** | `PROPAGATED` | A错误经回退传播到B | Backend失败 → 回退到API → API重新执行也失败 |
| **关联因果** | `CORRELATED` | A和B有共同根因但无直接因果 | 两个模块都因同一个LLM超时而失败 |

### 7.2 因果链构建

```
错误发生时：
  1. 检查是否存在root_error_id
     - 若当前错误是由A5回退触发的 → root_error_id指向触发回退的原始错误
     - 若当前错误是独立的 → root_error_id = null

  2. 检查是否存在related_error_ids
     - 同一错误簇内的错误互相关联
     - 同一模块在同一时间窗口内的错误互相关联

  3. Orchestrator维护因果链图
```

### 7.3 因果链存储

```json
{
  "causal_chain_id": "uuid",
  "pipeline_id": "uuid",
  "root_error_id": "err-001",
  "chain": [
    {
      "error_id": "err-001",
      "error_code": "API_DEF_CONFLICT",
      "agent": "backend_agent",
      "timestamp": "2026-04-30T00:15:00+08:00",
      "causes": []
    },
    {
      "error_id": "err-002",
      "error_code": "ROLLBACK_DEPTH_EXCEEDED",
      "agent": "orchestrator",
      "timestamp": "2026-04-30T00:20:00+08:00",
      "causes": [
        {"error_id": "err-001", "type": "PROPAGATED"}
      ]
    }
  ],
  "total_errors": 2,
  "max_depth": 2,
  "final_outcome": "L4_manual_intervention"
}
```

### 7.4 因果链深度限制

| 限制 | 值 | 说明 |
|------|---|------|
| 最大因果链深度 | 4 | 对应A5的MAX_ROLLBACK_DEPTH=2，每级回退最多产生2层因果 |
| 超深因果链处理 | 标记final_outcome=L4 | 因果链过深说明问题根因复杂，需人工介入 |

## 12. 错误数据查询

### 12.1 查询场景

| 查询者 | 查询场景 | 查询维度 |
|--------|---------|---------|
| **Orchestrator** | 决定是否触发断路器 | 按Agent+错误级别+时间窗口聚合 |
| **Orchestrator** | 评估回退影响 | 按因果链追溯根因和影响范围 |
| **Agent** | 修复时了解错误上下文 | 按error_id查询单条记录 |
| **用户** | 查看管线错误 | 按时间线+严重级别过滤 |

### 12.2 查询接口

错误数据通过文件读取+内存过滤实现，不需要数据库：

```python
class ErrorQuery:
    """错误数据查询工具"""

    def __init__(self, errors_dir: str):
        self.errors_dir = errors_dir
        self._cache: dict[str, dict] = {}

    def _load_agent_errors(self, agent: str) -> dict:
        """加载指定Agent的错误记录集"""
        if agent in self._cache:
            return self._cache[agent]

        path = os.path.join(self.errors_dir, f"{agent}_errors.json")
        if not os.path.exists(path):
            return {"errors": [], "summary": {}}

        with open(path, 'r', encoding='utf-8') as f:
            data = json.load(f)

        self._cache[agent] = data
        return data

    def query_by_level(self, agent: str, level: str) -> list[dict]:
        """按异常级别查询错误"""
        data = self._load_agent_errors(agent)
        return [e for e in data["errors"] if e["error_level"] == level]

    def query_by_code(self, agent: str, error_code: str) -> list[dict]:
        """按错误码查询错误"""
        data = self._load_agent_errors(agent)
        return [e for e in data["errors"] if e["error_code"] == error_code]

    def query_by_lifecycle(self, agent: str, state: str) -> list[dict]:
        """按生命周期状态查询错误"""
        data = self._load_agent_errors(agent)
        return [e for e in data["errors"]
                if e.get("lifecycle", {}).get("state") == state]

    def query_by_cluster(self, cluster_id: str) -> list[dict]:
        """按错误簇查询所有关联错误"""
        results = []
        for filename in os.listdir(self.errors_dir):
            if not filename.endswith("_errors.json"):
                continue
            agent = filename.replace("_errors.json", "")
            data = self._load_agent_errors(agent)
            for e in data["errors"]:
                if e.get("cluster_id") == cluster_id:
                    results.append(e)
        return results

    def query_unresolved(self, agent: str = None) -> list[dict]:
        """查询未解决的错误"""
        results = []
        agents = [agent] if agent else [
            f.replace("_errors.json", "")
            for f in os.listdir(self.errors_dir)
            if f.endswith("_errors.json")
        ]
        for a in agents:
            data = self._load_agent_errors(a)
            for e in data["errors"]:
                state = e.get("lifecycle", {}).get("state", "")
                if state not in ("resolved", "archived"):
                    results.append(e)
        return results

    def compute_metrics(self) -> dict:
        """计算错误指标（D4第10节）"""
        # 实现略，按第10.2节格式输出
        pass
```

## 13. 错误数据归档

### 13.1 归档策略

错误数据的归档遵循D2第9节的归档框架，但有以下特殊规则：

| 数据 | 归档策略 | 原因 |
|------|---------|------|
| 已解决的L1错误 | 仅保留指标摘要，删除详细记录 | L1错误通常是噪音，指标已足够 |
| 已解决的L2错误 | 保留记录，压缩存储 | 修复记录对Bug-Fix对库有价值（RAG体系） |
| L3/L4错误 | 完整保留 | 回退和人工介入的记录有审计价值 |
| 错误簇 | 保留聚合记录，删除被聚合的L1错误详情 | 聚合记录已是充分摘要 |
| 因果链 | 完整保留 | 根因分析需要完整因果链 |
| error_metrics.json | 完整保留 | 指标用于跨管线对比 |

### 13.2 归档后存储预估

| 数据类型 | 归档前 | 归档后 | 压缩比 |
|---------|--------|--------|--------|
| L1错误详情 | ~5KB | 0（仅留指标） | 100% |
| L2错误详情 | ~10KB | ~3KB | 70% |
| L3/L4错误详情 | ~5KB | ~5KB | 0%（完整保留） |
| 错误簇 | ~2KB | ~2KB | 0% |
| 因果链 | ~1KB | ~1KB | 0% |
| 错误指标 | ~2KB | ~2KB | 0% |
| **总计** | ~25KB | ~13KB | ~48% |

### 13.3 归档时Bug-Fix对提取

L2错误归档时，提取修复前后对比作为Bug-Fix对库的素材：

```json
{
  "bug_fix_id": "uuid",
  "extracted_from": "err-002",
  "pipeline_id": "uuid",
  "error_code": "STATIC_ANALYSIS_FAILED",
  "rule": "F821",
  "bug_description": "undefined name 'role_id' in user_service.py:42",
  "fix_description": "添加role_id参数到list_users方法签名",
  "bug_snippet": "def list_users(self, page, size):\n    ...",
  "fix_snippet": "def list_users(self, page, size, role_id=None):\n    ...",
  "extracted_at": "2026-04-30T00:35:00+08:00"
}
```

> Bug-Fix对提取是Advanced RAG体系的一部分，提取后的数据写入Bug-Fix对库（R7知识库质量规范定义具体存储格式）。

## 14. 错误数据与容错配置的联动

### 14.1 错误指标驱动容错配置调整

基于错误指标，可动态调整A5第8节的容错配置：

```json
{
  "fault_tolerance": {
    "dynamic_adjustments": [
      {
        "trigger": "l1_auto_recovery_rate < 0.5",
        "adjustment": {"max_file_retry": 2, "retry_interval_base_ms": 2000},
        "reason": "L1自愈率低，增大重试间隔避免LLM持续限流"
      },
      {
        "trigger": "l2_fix_success_rate < 0.3",
        "adjustment": {"max_fix_rounds": 2},
        "reason": "L2修复成功率低，减少无效修复轮次"
      },
      {
        "trigger": "cluster_avg_size > 3",
        "adjustment": {"module_failure_threshold": 1},
        "reason": "错误簇过大，降低模块级断路器阈值"
      }
    ]
  }
}
```

### 14.2 配置调整流程

```
管线运行中，每完成一个阶段：
  │
  ├─ 1. 计算错误指标（D4第10节）
  │
  ├─ 2. 检查是否触发动态调整条件
  │
  ├─ 3. 若触发：
  │     a. 记录调整原因到error_metrics.json
  │     b. 更新容错配置（A5第8节）
  │     c. 下一个Agent的dispatch消息中携带新配置
  │     d. 不影响当前正在运行的Agent
  │
  └─ 4. 管线完成后，将动态调整记录归入post-mortem报告
```

## 15. 错误数据在Prompt中的注入

### 15.1 注入策略

错误数据作为Agent Prompt的一部分，辅助Agent在修复/重新生成时避免重复错误：

| 场景 | 注入内容 | 注入位置 |
|------|---------|---------|
| L2修复 | 当前错误的error_code + message + affected_files | Prompt-Tail（修复指令） |
| L3回退后重新执行 | 触发回退的错误信息 + additional_context | Prompt-Head（回退上下文） |
| 断点续执行 | 上次执行的错误摘要 | Prompt-Head（续执行上下文） |
| D3降级后执行 | 降级模块列表 + 降级原因 | Prompt-Tail（降级约束） |

### 15.2 Token预算

错误数据注入占用A4定义的Token预算中的"Prompt"部分：

| 档位 | 错误数据Token预算 | 说明 |
|------|-----------------|------|
| 紧凑(8K) | ≤ 200 tokens | 仅注入error_code和message |
| 标准(32K) | ≤ 500 tokens | 注入error_code+message+affected_files |
| 宽裕(128K) | ≤ 1000 tokens | 注入完整错误记录+因果链摘要 |

### 15.3 错误数据注入格式

```
[错误上下文]
上次执行出错，请避免重复：
- 错误码: STATIC_ANALYSIS_FAILED
- 错误信息: app/services/user.py:42 undefined name 'role_id'
- 已尝试修复: 3轮
- 建议处理: 确保list_users方法签名包含role_id参数
```

## 16. 错误数据的完整性保障

### 16.1 一致性校验

错误数据需要与管线状态保持一致：

| 校验项 | 校验方法 | 不一致时处理 |
|--------|---------|------------|
| pipeline_state.json.errors与errors/目录 | 对比error_id集合 | 以errors/目录为准（权威源） |
| 错误簇中的error_ids是否都存在 | 遍历簇内ID | 删除不存在的ID引用 |
| 因果链中的error_ids是否都存在 | 遍历链内ID | 标记为dangling引用 |
| lifecycle状态是否合法 | 按第5.3节状态机校验 | 修正为最近合法状态 |

### 16.2 故障恢复中的错误数据

Orchestrator崩溃恢复时（D3第10.3节），错误数据需与管线状态同步恢复：

```
Orchestrator恢复流程中：
  1. 读取pipeline_state.json，确认current_stage和status
  2. 读取errors/目录，加载所有Agent错误记录
  3. 对比pipeline_state.errors和errors/目录：
     a. 一致 → 正常恢复
     b. errors/有而pipeline_state没有 → 补充到pipeline_state
     c. pipeline_state有而errors/没有 → 从pipeline_state重建错误记录
  4. 检查所有active状态的错误（lifecycle≠resolved且≠archived）：
     a. 有active错误 → 需要恢复容错流程
     b. 无active错误 → 正常续执行
```
